## C. IIS configuration (Phase 5/13-C)

### Site 1 — `ERP-API`
- Physical Path: `C:\IIS\ERP\API`
- Binding: `http`, Port `81` → `http://localhost:81`
- Application Pool: `ERP-API`
  - .NET CLR Version: **No Managed Code**
  - Managed Pipeline Mode: **Integrated**
  - Identity: **ApplicationPoolIdentity**

### Site 2 — `ERP`
- Physical Path: `C:\IIS\ERP\APP`
- Binding: `http`, Port `8080` → `http://localhost:8080`
- Application Pool: `ERP`
  - .NET CLR Version: **No Managed Code**
  - Managed Pipeline Mode: **Integrated**
  - Identity: **ApplicationPoolIdentity**

### Environment (Phase 9)
Both `LocalIIS.pubxml` profiles now set `EnvironmentName=Production`, which the SDK bakes into each published `web.config` as an `ASPNETCORE_ENVIRONMENT=Production` entry — no manual IIS environment-variable configuration needed. (Even without this, ASP.NET Core defaults to `Production` when the variable is unset — this just makes it explicit and self-documenting in the published output.)

### SQL Server access for the App Pool identity — required, easy to miss
Your connection string uses Windows Authentication (`Trusted_Connection=True`). Under IIS, the process runs as **`IIS AppPool\ERP-API`**, not your own Windows login — that virtual account needs its own SQL Server login with `db_owner` (or equivalent) rights on `ProsaecTotalDB`, or every DB call fails immediately with a login error. In SQL Server Management Studio:
```sql
CREATE LOGIN [IIS AppPool\ERP-API] FROM WINDOWS;
USE ProsaecTotalDB;
CREATE USER [IIS AppPool\ERP-API] FOR LOGIN [IIS AppPool\ERP-API];
ALTER ROLE db_owner ADD MEMBER [IIS AppPool\ERP-API];
```

## D. ASP.NET Core Hosting Bundle (Phase 6) — run yourself, do not assume it's installed

1. On the IIS machine, run `dotnet --info` and confirm a `Microsoft.NETCore.App 9.x` runtime is listed under "installed runtimes" **for the machine**, not just your dev SDK.
2. Open IIS Manager → Modules (at the server level, not a site) and confirm **AspNetCoreModuleV2** is listed. If it's missing, the ASP.NET Core Hosting Bundle isn't installed on this machine.
3. If missing: download and install the **.NET 9 Hosting Bundle** (not just the runtime) from Microsoft's download page, then run `net stop was /y` followed by `net start w3svc` (or simply restart the IIS service) so IIS picks up the module.

## E. Folder permissions (Phase 7) — minimum, not Full Control

Grant **Modify** (not Full Control) to `IIS AppPool\ERP-API` / `IIS AppPool\ERP` only on the specific subfolders each app actually writes to:

| Folder | Needed by | Grant to |
|---|---|---|
| `C:\IIS\ERP\APP\wwwroot\Uploads\EmployeeDocuments` | Employee document uploads | `IIS AppPool\ERP` |
| Any Excel export/temp folder used by `IExcelEngine`/ClosedXML (confirm exact path in `APP/Excel/ExcelEngine.cs` if it writes to disk rather than streaming in-memory) | Excel import/export | `IIS AppPool\ERP` |
| A `logs` folder if you enable stdout logging (see below) — e.g. `C:\IIS\ERP\API\logs` | ASP.NET Core Module stdout log | `IIS AppPool\ERP-API` |

Everything else under `C:\IIS\ERP` only needs **Read & Execute**, which `IIS_IUSRS` already has by default — don't widen this.

Note: your `ErrorLog` implementation writes to the database via `ApplicationDbContext` (`IErrorLogService`/`ErrorLogService`), not to a file — so it needs no filesystem permission beyond the SQL access already covered in section C.

## F. Error diagnostics (Phase 8) — troubleshooting table (Phase 13-D)

| Error | Typical cause | Fix |
|---|---|---|
| **500.19** | `web.config` malformed or a locked section | Check Windows Event Viewer → Application log; ensure `applicationHost.config` allows the sections web.config uses |
| **500.30 (start failure)** | App threw during startup — most often a missing/invalid connection string, SQL login failure, or the `Jwt:Key` missing check throwing | Temporarily enable stdout logging (below) and re-request the site; read the generated log in `C:\IIS\ERP\API\logs\stdout*.log` |
| **500.31 (ANCM Failed to Find Native Dependencies)** | Published as framework-dependent but the matching .NET runtime isn't installed on the server | Install the .NET 9 Hosting Bundle (Section D); confirm with `dotnet --info` |
| **502.5 (ANCM Out-Of-Process Startup Failure)** | App crashed before binding to a port — usually an unhandled startup exception | Same as 500.30: enable stdout logging temporarily, check Event Viewer |
| **500 (generic, app running)** | Unhandled exception in a controller action | `UseGlobalExceptionMiddleware()` (API) / `UseExceptionHandler("/Home/Error")` (APP) should already catch these — check `ErrorLog` table in the DB for the recorded exception |

**Enabling stdout logging (temporary, for diagnosis only):** in the published `web.config`, set `stdoutLogEnabled="true"` and `stdoutLogFile=".\logs\stdout"` (create the `logs` folder and grant it Modify per Section E). **Turn this back to `false` once you've diagnosed the issue** — leaving it on writes a log file per worker-process recycle indefinitely.

**Where logs live:**
- App-level errors → your `ErrorLog` table in SQL Server (existing implementation, unchanged)
- ASP.NET Core Module stdout (startup-failure diagnosis only, temporary) → `C:\IIS\ERP\<API|APP>\logs\stdout*.log`
- IIS access/HTTP logs → `%SystemDrive%\inetpub\logs\LogFiles\W3SVC<siteid>\`
- Windows Application Event Log → Event Viewer, for ANCM-level crashes before your own logging is even initialized
